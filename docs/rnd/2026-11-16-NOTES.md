## Hardening: `approximateTokenCount` CPU fix (this PR)

Confirmed the bug is still live on `main`: `approximateTokenCount` (called by every
lossless reducer) classifies each regex-matched chunk by re-testing `match[0]` against
two MORE regexes, instead of using capturing groups in the single pass that already
found the chunk. Fix: `TOKEN_CHUNK_PATTERN` now captures the three alternatives
(word / symbol-run / whitespace-run) so the match's own group index does the
classification — zero extra scans per chunk. Added 14 pinned exact-value test cases
(`token-reduction.test.ts`) covering the whitespace/newline-counting, word, digit,
apostrophe, punctuation and multi-byte-CJK paths, so a future rewrite of this loop
cannot silently change what gets billed as "tokens saved."

**Verification:**
- `pnpm build` clean, `pnpm test`: 973/973 (was 959 + 14 new).
- `run-agent-ab.ts` and `run-cache-decomposition.ts` output byte-identical before vs
  after (diffed full stdout) — zero change to any published saving number.
- `evals/run-proxy-overhead.ts`, 3 runs each side on this container, fix stashed/
  unstashed to control for container noise:
  - before: MESH-added p50 43.03 / 39.79 / 40.23 ms (mean of p50s ≈ 41.0 ms)
  - after: MESH-added p50 36.13 / 35.62 / 36.93 ms (mean of p50s ≈ 36.2 ms)
  - **measured delta: ~12% lower added latency on this container (p50).** This is
    smaller than the ~31%/~28% individually claimed by the two unmerged 11-01/11-04
    commits — their "before" baseline (p50 62.70ms raw-proxied) was measured on a
    different, apparently slower moment on this same container; today's raw-proxied
    baseline p50 is ~41-44ms. Reporting what I actually measured today, not the old
    commit's number.
- Proxy overhead is still ~36ms added (p50) after this fix — the structural cost
  (per-lever before/after re-tokenization across the reducer pipeline, each lossless
  reducer re-running `approximateTokenCount` over its own before/after text) that
  11-04's note queued as "future hardening" is still open and is the next-biggest
  target. Next hardening night should profile `applyReducers` end-to-end (not just
  this one hot function) before reaching for a cache or memoization layer.
