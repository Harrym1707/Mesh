## New-lever research: autonomous long-horizon agents, retry loops

**Grounding (WebSearch, not invented).** Two searches before building
anything:

1. How do real agent frameworks structure a tool-call retry? Confirmed via
   Anthropic's own tool-use docs and LangGraph/LangChain retry-middleware
   docs: a failure comes back as a `tool_result` block (often
   `is_error: true`), fed back into history as data, and the model (or a
   retry policy) can retry with the same arguments. LangGraph's `RetryPolicy`
   and `toolRetryMiddleware` exist specifically because this is common.
2. What goes wrong when it loops? A widely shared write-up ("why your agent
   retries the same broken tool call forever") and a GitHub issue describing
   an agent that "retried the same broken call without end" both describe
   the exact shape this lever targets: an identical failure, retried with
   identical arguments, producing an identical error body — and because the
   Messages/Responses APIs are stateless, every one of those identical
   failures rides along, unchanged, in the full history resent on every
   later turn. The standard advice (cap retries, compact history) treats the
   symptom; nothing treats the duplicate itself.

**The gap, confirmed by reading the code before building anything.**
`evals/run-workload-matrix.ts`'s existing `autonomousAgent()` fixture
already gestures at "retries duplicate the failed context verbatim", but
glues the retry text into one sentence inside a single user message — not
the real shape. The real shape is a separate `tool_use`/`tool_result` turn
pair per attempt, and neither existing lossless lever reaches a duplicate
there: `duplicateContext` (`dedupeRepeatedBlocks`) only ever dedupes within
ONE message's text at a time; `crossTurnMemoryDedup` only reads a turn's
LEADING TEXT block (`leadingText()` in `reduce-request.ts`), and a
`tool_result` is never a turn's leading text — it is its own block type
inside a user-role "carrier" message that the existing lever's own helper
(`isToolResultCarrier`) is written to recognise and exclude.

**The lever: `crossTurnToolResultDedup` (new, opt-in, LOSSY).** Walks every
`{type: 'tool_result'}` block in the request, in order, via the existing
`transformUserToolResultBlocks` helper (shared with the fresh-result cap and
stale-history compaction, so it sees exactly the same tool-result shapes
those levers already agree on). Keeps a map of exact-byte body → first
occurrence; any later occurrence at or above `minimumBlockTokens` (default
64, same default as `crossTurnMemoryDedup`) is replaced with a short
reference marker (`[mesh: N tokens of this tool result, identical to tool
result K, omitted]`); the first occurrence and the `tool_use_id` pairing on
every message are always kept verbatim, so a retried call never loses its
required tool_use/tool_result pairing (an orphaned tool_use is a hard 400
from the provider — confirmed in the LangGraph search above — so this was a
correctness constraint on the design, not just a quality one). An
already-collapsed marker is never re-collapsed, so the lever is idempotent
across consecutive requests. Classified **LOSSY** for the same reason
`crossTurnMemoryDedup` is: the duplicate removed is not adjacent to its
twin, so it needs a `replayGate` pass on a customer's own traffic before any
part of its saving may be billed. Never on by default.

Implementation: `packages/sdk-js/src/reduce-request.ts` (config field
`crossTurnToolResultDedup`, function `dedupeToolResultsAcrossTurns`, wired
in the same pipeline slot as `crossTurnMemoryDedup` and for the same
reason — before the per-message pass, so it sees raw tool-result bodies).
9 new tests in `packages/sdk-js/src/reduce-request.test.ts` covering: the
core collapse-after-first-occurrence behaviour and the lossy change record,
that `tool_use` blocks and genuine user text are never touched, off by
default, a no-op on a single occurrence, the `minimumBlockTokens` threshold
and its invalid-value skip-the-whole-reduction behaviour (same contract as
every other lever here), that a Responses-style `function_call_output` item
is correctly left alone (it is not the one documented `tool_result` shape,
so this is a deliberate boundary, not a gap), collapsing three-or-more
retries all pointing back at the first occurrence, and idempotency.
1061 → 1070 tests, `pnpm build` clean.

**Measurement.** New eval `evals/run-retry-loop-dedup.ts`: a 24-turn
autonomous migration agent, full history resent every turn, with four of
those turns hitting a transient failure on the same tool that gets retried
2–4 times (schedule: turns 4/9/15/20, 2/3/2/4 failures respectively) before
succeeding, each retry producing the byte-identical error body. Three arms,
same convention as `run-memory-agent-dedup.ts`:

```
A. raw (no MESH)                tokens 159,738 -> 159,738  cost $0.3837
B. lossless stack                tokens 245,945 -> 247,236  cost $0.3837
C. B + crossTurnToolResultDedup  tokens 245,945 -> 231,625  cost $0.3529  (cross-turn-tool-result-dedup x48)

B vs A (lossless stack alone, QUALIFIED): 0.0%
C vs B (the new lever's OWN effect, LOSSY, candidate only): 8.0%
C vs A (full stack incl. the lossy lever, LOSSY, candidate only): 8.0%
```

B vs A is 0.0% by construction (both arms priced with caching unavailable,
isolating the new lever's token effect from the cache's own, same reasoning
as the memory-agent eval). B's token-counting going slightly UP
(245,945 → 247,236 before any lever runs, vs A's 159,738) is the same JSON-
framing artifact `2026-10-22-workload-matrix-findings.md` already flagged
for the cache stamp's block split — not model-visible content, and not this
lever's effect.

**Honest read: 8.0% is a real but modest candidate**, smaller than
`crossTurnMemoryDedup`'s measured 58.0% on its shape, because retries are a
minority of this fixture's turns (4 of 24) rather than every turn. It scales
with how often an account's agents actually hit this failure mode — which
is unmeasured on real traffic (the public-data-sources catalogue in
`docs/rnd/knowledge/2026-10-27-public-data-sources.md` has no retry-rate
field for any of the traces reviewed so far). **Not a qualified win. A
candidate**, reported at the measured band, same treatment as
`crossTurnMemoryDedup`.
