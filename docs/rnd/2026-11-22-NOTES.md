## Hardening: proxy overhead — found and fixed a real CPU sink

`node --import tsx evals/run-proxy-overhead.ts` on this machine (linux/x64,
container, loopback stub) measured MESH adding **p50 ≈36ms / mean ≈36-38ms**
per request — well above the ~22ms/~24ms darwin/arm64 figure evidence.md
quotes (that line is explicitly machine-relative — "absolute values vary by
machine, rerun the command on yours" — so the two numbers are not
comparable as a regression; different hardware). Profiled with
`node --prof` over 4,000 calls to `reduceRequest` using the same
multi-turn agent fixture the eval replays, with the eval's exact lossless +
5m-cache-stamp config.

**Finding:** `approximateTokenCount` (`packages/core/src/token-reduction.ts`,
the default token counter used whenever no provider tokenizer is supplied —
true for the proxy's default config and this eval) was the single largest
CPU cost inside `reduceRequest`, and most of *that* was redundant work: for
every chunk its `matchAll` split produced, the function ran the regex split
once to get the chunk, then ran **two more regex tests**
(`/^\s+$/.test(chunk)`, `/^[\p{L}\p{N}']+$/u.test(chunk)`) just to find out
which of the split's own three alternatives had matched — information the
split already had and was throwing away. In the `--prof` output those two
re-tests plus their `RegExpPrototypeTestFast` builtin accounted for
~19% of all profiled ticks on their own.

**Fix (lossless, lossless-first):** capture the three alternatives in the
split regex itself (`/([\p{L}\p{N}']+)|([^\p{L}\p{N}'\s]+)|(\s+)/gu`) and
branch on which capture group is defined, instead of re-testing the chunk
text. Same classification, same arithmetic, same output — this changes
*how* the function discovers which branch to take, not what it computes.
Verified with a new test (`token-reduction.test.ts`, "matches the
three-regex reference...") that runs both the new implementation and a
kept copy of the original three-regex version over eight varied samples
(empty, prose, punctuation, JSON, code, unicode/emoji, whitespace-heavy,
a 5KB stress string) and asserts identical counts. This is exactly the kind
of change the house rules call lossless by construction: nothing a model
or a customer could observe changes, only CPU spent computing it.

**Measured:**
- `reduceRequest` alone over 2,000 calls of the same fixture: **3.14ms →
  2.49ms per call (−20.7%)**, reproduced across two runs.
- `--prof` tick share of the token counter's regex work: ~52% of profiled
  ticks before (18.0% iterator + 9.8% split regex + 9.0%/5.6%/4.5% the two
  re-tests + their regex) → ~53% after, but now almost entirely the
  irreducible split itself (27.9% iterator + 14.0% split regex), the two
  re-test regexes gone.
- End-to-end `evals/run-proxy-overhead.ts` (same machine, stashed vs.
  applied, 2 runs each side immediately before/after to control for
  machine noise): **added p50 latency 35.2–37.3ms → 29.4–31.7ms, roughly a
  14–16% cut in MESH's own per-request overhead.** Direct-arm latency
  (no MESH) was unaffected in both runs, as expected — the fix only touches
  code that only runs inside `reduceRequest`.
- Full suite: 1206/1206 green, no eval regressions.

**What this is not:** not a token-count change (no published band moves),
not a lossy lever (no replay gate needed), not a claim about the
darwin/arm64 absolute figure in evidence.md, which I left untouched because
it is explicitly machine-relative and this container is a different
architecture. If someone re-runs `evals/run-proxy-overhead.ts` on the
