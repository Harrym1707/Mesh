## New-lever research: continuous-memory agents — closing Finding 1

Finding 1 from `docs/rnd/2026-10-22-workload-matrix-findings.md` has been on
every new-lever night's "what's owed" list since 2026-10-23 and was called
out again, explicitly, in `2026-10-25-NOTES.md`: `crossTurnMemoryDedup` (the
cross-turn memory dedup lever, `packages/sdk-js/src/reduce-request.ts`) has
a measured 58.0% candidate saving on the continuous-memory-agent shape
(`evals/run-memory-agent-dedup.ts`) that was never run through the actual
approval machinery — `packages/sdk-js/src/replay-gate.ts` — the thing that
decides whether a lossy lever may ever be billed. Tonight closes that out.

### What was built

1. **`evals/memory-agent-fixture.ts`** (new) — the shared fixture both the
   measurement eval and the new gate eval now import, factored out so they
   can never silently drift apart (the same reason `evals/agent-fixture.ts`
   exists for the freshcap gate). Adds, on top of the existing memory block
   and preamble (moved here from `run-memory-agent-dedup.ts`):
   - **Five distinct, independently-checkable facts**, each a verbatim
     substring of the memory block (deploy window, staging-DB Friday
     policy, incident root cause, checklist size, escalation contact). Each
     turn asks about one fact, cycling through them.
   - **A declared-assumption recall model** (`simulateRecall`): there is no
     real model in this harness, so correctness is defined as "the nearest
     verbatim restatement of the memory block is within
     `MEMORY_RECALL_HORIZON_TURNS` (5, a round, undefended constant) turns
     of the one asking." This is the same honesty move
     `run-replay-gate-freshcap.ts` already makes for the fresh-cap lever —
     a simulated model standing in for a real one — made explicit in a
     module-level comment so nobody downstream mistakes the verdict below
     for a measured quality number. **It is not one.** It exists to prove
     the gate mechanism draws the right line, pending a real replay-gate
     pass on a customer's own traffic.

2. **`restateEveryTurns` option**, added to `crossTurnMemoryDedup` itself
   (`packages/core/src/token-reduction.ts`'s `dedupeRepeatedLeadingBlock`,
   threaded through `packages/sdk-js/src/reduce-request.ts`'s
   `dedupeMemoryAcrossTurns`). The shipped lever only ever restates the
   memory block verbatim at turn 0, so the distance from "the model needs
   this fact" to "the nearest place it was actually said" grows without
   bound as a conversation runs long. `restateEveryTurns: N` re-anchors the
   block verbatim at every Nth turn too, capping that distance at N-1
   forever instead of letting it grow with conversation length. Still
   lossy, still gate-bound — this only changes HOW lossy, giving the gate
   something real to discriminate between a safe and an unsafe setting of
   the same lever, rather than a single all-or-nothing on/off switch.
   8 new unit tests across `token-reduction.test.ts` and
   `reduce-request.test.ts` (validation, the re-anchor points landing where
   expected, the option composing with the existing minimum-block-size
   guard). 523 → 534 tests.

3. **`evals/run-replay-gate-memory-dedup.ts`** (new) — the actual gate run,
   three candidates, `crossTurnMemoryDedup` in isolation (no other lever,
   so the verdict is about this lever alone):
   - `NAIVE` — the shipped default (no `restateEveryTurns`).
   - `BOUNDED_8` — `restateEveryTurns: 8` (max distance 7, over the fixture's
     5-turn horizon on 2 of every 8 turns).
   - `BOUNDED_4` — `restateEveryTurns: 4` (max distance 3, inside the horizon
     on every turn).

   Grader: `textSimilarityGrader` (`packages/sdk-js/src/graders.ts`),
   reused as-is rather than inventing a new one — the simulated reply text
   already encodes correct/incorrect outcomes distinctly, so a degree-based
   text-overlap grader is the right existing tool. A matching test file
   (`run-replay-gate-memory-dedup.test.ts`, 7 tests) pins the recall model's
   own behaviour the way `run-replay-gate-freshcap.test.ts` pins its
   simulated provider — if these drift, the verdict below is noise, not
   evidence.

4. **One pre-existing latent bug fixed in passing**: adding these new
   files to the `typecheck:evals` script (they now are, alongside the
   existing freshcap pair) surfaced a real `--strict` narrowing failure
   already sitting in `evals/run-memory-agent-dedup.ts` — `price.price`
   used inside a nested function closure (`measureArm`) does not retain
   the module-scope `if (price.status !== "priced") throw` narrowing under
   TypeScript's control-flow analysis, because that file had never been
   added to the strict-checked list before tonight. Fixed the same way
   `run-replay-gate-freshcap.ts` already does it — captured as its own
   `const` right after the guard instead of read inline later — in both
   that file and the new gate script. No behavioural change: reran
   `run-memory-agent-dedup.ts` before and after, byte-identical output
   (58.0% candidate figure unchanged).

### Measured result

```
node --import tsx evals/run-replay-gate-memory-dedup.ts
```

| candidate | mean Δ | lower95 Δ | tokens saved | verdict |
|---|---|---|---|---|
| NAIVE (shipped default) | −67.70 pp | −75.94 pp | 76.5% | **REJECTED** |
| BOUNDED_8 | −19.92 pp | −29.89 pp | 68.6% | **REJECTED** |
| BOUNDED_4 | 0.00 pp | 0.00 pp | 58.9% | **APPROVED** |

**Finding, reported honestly, not inflated**: `crossTurnMemoryDedup` as
shipped today is **not safe to bill** under this fixture's (declared,
unmeasured) recall assumption — it fails the gate by a wide margin, not a
borderline one. Bounding it with `restateEveryTurns: 4` is a real fix: it
holds quality at exactly zero delta on this fixture while keeping 58.9% of
the saving (versus 76.5% unbounded) — a materially smaller number than the
NOTES-carried 58.0% "candidate", and the honest one to carry forward,
because it is the setting that actually clears a gate rather than the
setting that was merely measured. `BOUNDED_8` failing demonstrates the
boundary is a real cliff in this model, not an artifact of the gate always
passing bounded variants — tightening the restatement interval matters,
and the fixture can tell the difference.

### What this is NOT

A billable lever, yet. Every number above is simulator-measured against a
fixture whose "quality" signal is a declared assumption about recall decay
over conversational distance, explicitly not calibrated against any real
model (see the honesty label in `evals/memory-agent-fixture.ts`). What
tonight actually proves is narrower and still real: the replay-gate
*mechanism*, run with a reasonable stand-in grader, correctly separates an
unsafe lever configuration from a safer one, and the bounded configuration
is the one worth proposing to a customer's own replay-gate run — graded by
their task-completion signal or an LLM judge against real model output
both ways — before any part of this may be billed. That real run is the
next concrete step, not a future "someday": until it happens,
`crossTurnMemoryDedup`'s default stays off, and if it is ever recommended
to a customer it should be recommended with `restateEveryTurns` set, not
left unbounded.
