## Tonight's workload shape: multi-agent fan-out

Founder mandate shape 1: "multi-agent teams (sub-agent fan-out re-sending
shared context)". Per `docs/rnd/lever-backlog.md`, this shape already has a
fully designed candidate nobody had implemented or measured —
**P5, shared-prefix fan-out serialization** — so tonight builds that, rather
than starting a new design from scratch.

### How the request shape is actually structured (real framework behaviour)

- Checked the Claude Agent SDK's own subagents documentation
  (code.claude.com/docs/en/agent-sdk/subagents, read via WebFetch/WebSearch
  tonight): a parallel `Agent` tool call is "launched... simultaneously" when
  several are issued in one message — genuine concurrent dispatch, not a
  staggered loop. It also documents that a subagent's system prompt is its
  OWN (from its agent definition), **not inherited from the parent** — so the
  realistic model is several FRESH, same-role, same-tools sub-agent instances
  sharing a prefix with EACH OTHER, not a persistent per-role conversation
  carried turn-over-turn.
- Checked CrewAI's hierarchical process (WebSearch): parallelism there is
  inconsistent across sources — one guide claims hierarchical mode delegates
  independent tasks in parallel, Arize's own docs say CrewAI does not enforce
  true concurrent execution, and a live GitHub issue (#4783) reports
  delegation sometimes not firing at all. Not a clean citation for "always
  concurrent"; the Agent SDK's documented behaviour is the solid one and is
  what tonight's fixture follows.
- Checked for a published cache-write time-to-first-byte benchmark (WebSearch,
  Anthropic docs + several third-party posts): **none exists.** Every number
  found was either qualitative ("caching lowers TTFT") or an unsensible
  anecdote with no method. The latency model below is therefore explicitly an
  ESTIMATE, not a measurement — flagged everywhere it's used.

### The finding this surfaces: a substrate bug, not just a missing lever

`packages/core/src/cache-simulator.ts`'s `simulateCache` assumed a cache
WRITE becomes instantly readable by any other request the moment it is sent.
Real provider behaviour (and the backlog's own framing of P5) is that the
entry exists only once that write's own response has started. The simulator
had no concept of that gap at all: two requests at the exact same `atSeconds`
already looked like "one write, one read" with zero elapsed time and zero
lever code. That means **the P5 lever this night builds was already being
simulated, for free, always-on, by accident**, for any workload bursty
enough to create same-instant requests — multi-agent fan-out being exactly
that workload. This is why 2026-10-22's workload-matrix finding for
multi-agent (−55.6% cost, `docs/rnd/2026-10-22-workload-matrix-findings.md`)
looked as good as it did: the uncorrected simulator was secretly assuming the
lever had already shipped.

### What shipped tonight

1. **`packages/core/src/cache-simulator.ts` — concurrency semantics (the
   backlog's own stated prerequisite for P5).** Added an optional
   `writeAvailabilityLatencySeconds?: (writtenPrefixTokens: number) => number`
   field on `CachePolicy`. An `Entry` now carries `availableAt`; a request can
   only match an entry with `entry.availableAt <= request.atSeconds` — an
   entry whose write has not yet reached first-response-start is invisible to
   everyone else, however identical its prefix. New `missReason`:
   `"racing-write"` (entries exist, none visible yet — distinct from
   `"expired"`/`"first-request"`). **Every existing `CachePolicy` export is
   unchanged** (no latency function set), so every pre-existing simulation —
   including every one behind a published figure — reproduces exactly: 4 new
   tests in `cache-simulator.test.ts`, 26/26 passing, 22 pre-existing ones
   untouched. Confirmed empirically, not just reasoned: re-ran
   `run-agent-ab.ts` / `run-cache-decomposition.ts` after the change,
   byte-identical output.

2. **`packages/sdk-js/src/fanout-serializer.ts` — the actual lever.** A
   `FanoutSerializer` in-flight latch: `admit(key)` resolves `true` for the
   first caller on a key (who must `release(key)` itself once its own
   response starts, or on error) and holds every other caller for that key
   until release, a cap elapses, or the key is already settled. Fails open
   by construction — a hold past `maxHoldMs` (default 5000ms) or the first
   request's own error path releases every waiter, so a stall here can never
   become a client-visible failure, matching the proxy's existing "nothing
   here may break a request" rule. `cacheablePrefixKey(request)` hashes
   `[model, tools, system]` — the exact span the provider's longest-prefix
   match covers before message content, same idea as
   `CachePrefixVolatilityGuard`'s own prefix hash. Pure timing change, no
   byte the model reads is touched — lossless, no replay gate. 12 new unit
   tests in `fanout-serializer.test.ts`.

3. **Wired into the real proxy** behind a new, default-OFF
   `serializeFanoutWrites` option on `MeshProxyOptions` (plus
   `fanoutHoldCapMs`). In `packages/sdk-js/src/proxy.ts`: before the upstream
   `fetch`, the reduced request's prefix key is computed and admitted; the
   gate is released the moment `fetch` resolves (response headers arrived)
   or throws (upstream error) — but only by whichever call was first, so a
   released waiter never tears down a different request's gate. 3 new
   integration tests in `proxy.test.ts` against a stub upstream that delays
   its first response by 150ms: with the flag on, 4 of 5 concurrent
   same-prefix requests are provably held until the first's response starts
   (margin-tested on real elapsed wall-clock time, not mocked); with the
   flag off, all 5 reach the upstream within <100ms of each other (today's
   unchanged behaviour); and a dead upstream's error releases waiters well
   under the hold cap rather than making them wait it out.

4. **`evals/run-fanout-serialization.ts` — the fixture and the honest
   measurement.** A fixture of 8 independent fan-out bursts (5 fresh,
   same-role sub-agents each, ~5–22ms dispatch jitter within a burst, bursts
   400s apart so each is a genuine cold start past the 300s TTL — not a
   persistent per-agent conversation like the EXISTING `multiAgentTeam()` in
   `run-workload-matrix.ts`, which spaces agents 4 SECONDS apart and so never
   actually races under either the old or the new simulator). Three arms,
   same requests, same catalogue price:

   | arm | mechanism | cost | hit rate | vs uncached |
   |---|---|---|---|---|
   | 0: today (uncorrected sim) | no concurrency concept | $0.1406 | 79.5% | **+47.2%** |
   | 1: corrected, NO lever | racers each pay the write premium | $0.3109 | 0.0% | **−16.7% (a LOSS)** |
   | 2: corrected, WITH lever (FanoutSerializer re-timing) | N−1 writes → N−1 reads | $0.1406 | 79.5% | **+47.2%** |

   Arm 0 and arm 2 are identical to four decimal places — direct proof the
   old simulator was quietly crediting this exact, not-yet-built lever.
   Arm 1 is the honest "do nothing" baseline, and it is **a net loss** on
   this fixture (racers always pay 1.25x, never read) — the opposite of what
   the old simulator reported. **Lever credit, measured against the honest
   baseline**: $0.1703, 54.8% of arm 1's cost, on this fixture specifically
   (32 of 40 requests were racers; the shared prefix is 2,210 tokens, diluted
   by each agent's own unique task text in the aggregate number). Isolated to
   just the shared-prefix tokens, per converted racer: write $0.00553 vs read
   $0.00022 = 96.0% — close to the backlog's own reasoned 92% estimate
   ((1.25−0.1)/1.25), the small gap being OpenAI-vs-Anthropic-style minimum
   rounding, not a different mechanism.

### Honesty labels (per the mandate — nothing here is overclaimed)

  tokens/15,000 tok/s assumed prefill throughput) are an **ESTIMATE**: no
  provider publishes this number (checked tonight, see above). They are
  order-of-magnitude reasoned, not measured, and every eval line that depends
  on them says so.
  - **Open ask for the next night with WebFetch or live-capture access**: a

    Anthropic calls sharing an identical, ≥1,024-token system+tools block —

    on the racers and replace this estimate with a measurement. This is the
    same "one cheap live A/B validates the flip" the backlog already asks
    for; tonight did not have upstream Anthropic credentials wired into this
    environment to run it.
- **Collision frequency is still the top missing input**, exactly as the
  backlog says, and tonight's fixture does not resolve that — it ASSUMES 8
  independent cold-start bursts; it does not derive that count from any real
  traffic sample. The per-racer 96% figure is solid (it's just arithmetic on
  documented multipliers); the aggregate 54.8% is only as good as "how often
  does a cold multi-agent fan-out actually happen," which nobody has measured.
- The lever is genuinely lossless (timing only); no quality gate or replay
  gate applies, matching the backlog's own classification.
