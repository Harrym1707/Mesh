## New-lever research: the multi-agent fan-out cache race (lever-backlog.md P5)

### Why this shape, tonight

`docs/rnd/lever-backlog.md`'s P5 ("Shared-prefix fan-out serialization") is
rated **the most genuinely lossless lever in the portfolio** but was still
sitting in PURSUE with its own measurement plan unstarted: "Timestamped
multi-agent capture is a prerequisite and remains the top missing input."
`evals/run-workload-matrix.ts`'s existing "multi-agent team" fixture
staggers each agent's call by 4s within a round specifically to avoid this
— it measures a different, sequential-trickle shape and has never exercised
the race at all. Nobody had built the concurrent fixture, fixed the
simulator to model it, or shipped the mechanism side of the lever. Tonight
does all three.

### Grounding (WebSearch + WebFetch, 2026-11-18, both sources load-bearing)

- **Anthropic's own docs**, "Cache limitations"
  (platform.claude.com/docs/en/build-with-claude/prompt-caching): *"For
  concurrent requests, note that a cache entry only becomes available after
  the first response starts. If you need cache hits for parallel requests,
  wait for the first response before sending subsequent requests."* This is
  the exact mechanism P5 described from documented semantics, now a direct
  quote, and the exact mitigation ("wait for the first response") is the
  lever this night implements.
- Same page: **the per-model cacheable minimum has moved since this
  codebase's `anthropicCacheableMinimumTokens` was captured.** The live page
  lists **512 tokens** for Claude Sonnet 5.5 and Opus 5.5 (the exact models
  every published figure in this repo prices), and separately lists Haiku
  5.5 at 512 and Haiku 4.5 at 4,096 — not the flat 1,024/2,048 split
  `model-prices.ts` encodes (captured 2026-10-08, per its own doc comment).
  The **read multiplier is already correct**: the catalogue's
  `cachedInputPerMillion` for Sonnet 5.5 (0.1 of a $2 input rate = 0.05x) and
  Opus 5.5 (0.2 of $4 = 0.05x) already matches the page's stated 0.05x
  exception for those two models, because `simulateCache` prefers
  `price.cachedInputPerMillion` over the policy's generic multiplier — so
  nothing is mis-PRICED today. What is stale is the MINIMUM:
  `cache-simulator.ts`'s `ANTHROPIC_CACHE_5M`/`ANTHROPIC_CACHE_1H` hardcode
  `minimumCacheableTokens: 1_024` for every model, and
  `model-prices.ts`'s `anthropicCacheableMinimumTokens` returns 1,024 for
  anything not matching `/haiku/i`. If the live page is right, prefixes in
  roughly [512, 1024) tokens that this repo currently treats as
  below-minimum (suppressed, per the 2026-10-25 hardening fix) may actually
  be cacheable on Sonnet 5.5/Opus 5.5 today, which would UNDER-claim, not
  overclaim, on some shapes — the opposite direction from most of this
  repo's corrections, and exactly why it needs its own careful night rather
  than a tonight side-fix: changing a billing-critical minimum deserves the
  same "live-probed before activation" rigor the backlog's P6 already
  demands, a single WebFetch is not that, and this doc comment's own capture
  date (2026-10-08) might predate a real provider change rather than being
  simply wrong. **Flagged for next night's verification, not changed
  tonight.** See "What the next night should try" below.
- **The Claude Agent SDK's own subagents doc**
  (code.claude.com/docs/en/agent-sdk/subagents): *"Parallelization: multiple
  subagents can run concurrently, so independent subtasks finish in the
  time of the slowest one rather than the sum of all of them. During a code
  review, you can run style-checker, security-scanner, and test-coverage
  subagents simultaneously instead of sequentially."* Spawned via "multiple
  Task tool calls in a single message," with a documented default
  concurrency cap of 20 subagents at once (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`).
  This is the real shape: an orchestrator firing N sub-agent calls in one
  instant, sharing one system+tool prefix (the prefix is genuinely shared —
  Anthropic's own orchestration example notes the top-level `system` field
  never changes across subagent calls) with distinct per-agent task content.
  CrewAI and LangGraph's docs (also searched) describe the same fan-out
  pattern at the framework level but gave no detail specific enough to cite
  verbatim; the Claude Agent SDK's own docs were the strongest, most
  specific source and are what the fixture is built from.

### What was built

1. **`packages/core/src/cache-simulator.ts`**: `SimulatedRequest` gained an
   optional `respondsAfterSeconds` field (time-to-first-byte). A cache entry
   is now only matchable once `entry.availableAt` (`atSeconds +
   respondsAfterSeconds` at the time it was written) has passed — before
   tonight, every entry was available to every other request the instant it
   was pushed, regardless of whether a real response had actually started.
   Omitting the field (every existing caller) reproduces the prior behaviour
   exactly: confirmed by `run-agent-ab.ts` and `run-cache-decomposition.ts`
   printing byte-identical numbers before and after. Four new tests in
   `cache-simulator.test.ts` cover the race, a correctly-timed hold
   recovering the read, an under-sized hold still losing the race, and the
   default-omitted backward-compatibility case.
2. **`packages/sdk-js/src/fanout-latch.ts`** (new, exported from the
   package index): `FanoutLatch`, a lossless coordination primitive. The
   first caller on a given prefix key ("leader") dispatches immediately;
   every later caller on that key ("follower") waits for the leader's
   dispatch to settle (success, failure, or a caller-supplied `holdCapMs`,
   whichever comes first) before making its OWN real call — never reusing
   the leader's response, only timing its own call later. Bytes sent are
   unchanged; only send timing moves, which is why this is lossless and
   carries no replay-gate requirement. 8 unit tests: leader dispatches
   immediately, a follower is held and released on leader success, released
   immediately (not after the full hold cap) on leader failure, released
   after the hold cap when the leader never settles, independent prefix
   keys never block each other, a settled leader's key is free for a fresh
   leader, and multiple followers release together.
3. **`packages/sdk-js/src/proxy.ts`**: new opt-in `MeshProxyOptions.fanoutLatch?:
   { holdCapMs: number }`, off by default (confirmed: all 18 pre-existing
   proxy tests pass unchanged with it unset). When set, it applies ONLY to
   Anthropic requests MESH actually stamped with `cache-ttl-5m`/`cache-ttl-1h`
   (checked via `summary.changes`) — nothing else races on a cache entry, so
   nothing else is touched. The prefix key is a SHA-256 of
   `[model, tools, system]` on the REDUCED request (the bytes actually sent),
   matching the same {tools, system} shape `CachePrefixVolatilityGuard`
   already uses for its own prefix identity. 2 new integration tests
   against a real HTTP stub that delays its response: with `fanoutLatch`
   configured, a follower's upstream request provably arrives only after
   the leader's response has started (measured via real arrival
   timestamps, generous margin); with it omitted, both arrive within a few
   ms of each other, confirming the default path is untouched.
4. **`evals/run-fanout-race.ts`** (new): the measurement fixture. A shared
   system+tool prefix sized like `run-workload-matrix.ts`'s multi-agent
   fixture (~2,000 tokens, comfortably above the 1,024-token minimum this
   repo currently uses), fanned out to 3/5/10 sub-agents (the SDK's own
   example is 3; its default cap is 20) all fired at the same instant. Five
   arms per racer count: uncached; what the PRE-FIX simulator would have
   reported (instant availability); the honest default (stamped, raced, no
   coordination); a FanoutLatch hold cap sized to half the true TTFB
   (under-provisioned); and a correctly-sized FanoutLatch. TTFB itself has
   no live measurement for a prefix this size anywhere in this repo (flagged
   below, same gap P5 already named) — one representative ESTIMATE (1.5s)
   is used and the result is checked to not depend on its exact value
   (confirmed in code: `anyConfirmedLoss` assertions), only its sign.

### Measured result (simulator-measured, catalogued claude-sonnet-5-5 prices)

```
n=3:   uncached $0.0187 | old-sim(overclaimed) $0.0121 | raced $0.0217 (+16.2% vs uncached -- A LOSS) | under-held $0.0217 (no saving) | latched $0.0121 (-35.3% vs uncached, -44.3% vs raced)
n=5:   uncached $0.0311 | old-sim(overclaimed) $0.0169 | raced $0.0362 (+16.2% vs uncached -- A LOSS) | under-held $0.0362 (no saving) | latched $0.0169 (-45.6% vs uncached, -53.2% vs raced)
n=10:  uncached $0.0623 | old-sim(overclaimed) $0.0290 | raced $0.0723 (+16.2% vs uncached -- A LOSS) | under-held $0.0723 (no saving) | latched $0.0291 (-53.4% vs uncached, -59.8% vs raced)
```

**Two findings, not one:**

1. **CONFIRMED NEGATIVE** (per the founder mandate: "a lever that loses
   money counts against FLUX"): the existing, already-shipped `cache-ttl-5m`
   lever, applied with no concurrency awareness to genuinely simultaneous
   same-prefix fan-out, is a **net loss versus not caching at all** — every
   racer writes (1.25x base) and none read (0.05x base on Sonnet 5.5), and a
   write costs more than the uncached base rate. This is +16.2% worse than
   doing nothing, on every racer count tested, and is real today on any
   customer running something shaped like the Claude Agent SDK's own
   documented parallel-subagent pattern through MESH's cache stamp with no
   coordination. This is NOT hypothetical or gated behind the new lever —
   it is a property of the lever that already ships, newly measurable now
   that the simulator can see concurrency at all.
2. **The old (pre-tonight) simulator overclaimed the multi-agent band by
   44–60%** on this fixture (compare `old-sim` to `raced` above) — it let
   every racer after the first instantly read a cache entry the real
   provider would not have written yet. Per the backlog's own instruction
   ("restate the multi-agent band under them first — it will come down"),
   this is that restatement. No PUBLISHED number moves: this fixture never
   fed README/evidence.md's headline figures (those come from
   `run-agent-ab.ts`'s sequential, non-racing traffic, confirmed
   byte-identical above), but anyone who mentally extrapolated the existing
   multi-agent band to concurrent fan-out was relying on an assumption the
   simulator could not actually check until tonight.
3. **The fix (`FanoutLatch`) turns the loss back into a win**: a correctly
   sized hold cap recovers the saving the old simulator had wrongly assumed
   was already happening for free (compare `latched` to `old-sim` above —
   they match, which is the right outcome: the latch's whole job is to make
   the honest cost equal the previously-wrong optimistic one). An
   under-sized hold cap (released before the true TTFB) buys nothing at all
   — the sizing has to be right or the lever is a no-op, not a partial win.

### Quality gate / replay-gate status

None needed. Nothing sent to the provider changes — `FanoutLatch` only
changes WHEN a request is dispatched, never its bytes. This is the same
category as the existing cache-TTL stamp itself: a billing-rate lever, not
a content transform, so it carries no replay-gate requirement by
construction (same reasoning the 2026-10-25 note gave for the below-minimum
suppression guard).

### What was NOT done tonight (deliberately, to keep blast radius bounded)

- **`FanoutLatch` is not validated on real traffic.** It ships off by
  default, gated behind `MeshProxyOptions.fanoutLatch`, with the same
  "not yet validated" posture `docs/rnd/theo-operating.md` already uses for
  Theo's `optimise` autonomy level. `holdCapMs` has no default and must be
  sized from a real measurement of the shared prefix's own cold-write TTFB
  — this repo has none yet (same gap the backlog already named for P5).
  Shipping it live-default, or picking a holdCapMs out of thin air, would
  trade a measured pricing risk for an unmeasured latency/timeout risk,
  which the backlog's own adversarial conditions for P5 explicitly warn
  against (hold-time watchdogs, release-on-error, timeout-under-client-TTFB).
- **`evals/run-workload-matrix.ts`'s "multi-agent team" fixture was left
  untouched.** It measures a real but different (sequential, 4s-staggered)
  shape; replacing or extending it to also cover true concurrency is a
  reasonable follow-up once `FanoutLatch` has had a review pass, not a
  same-night change to a fixture that feeds the published workload-matrix
  table.
- **The Sonnet 5.5 / Opus 5.5 cacheable-minimum discrepancy** (512 tokens
  per the live docs fetched tonight vs. this repo's 1,024) was NOT corrected.
  It is a billing-critical constant; correcting it needs the same live-probe
  discipline P6 already specifies, not a single WebFetch acted on in the
  same night it was noticed.
- **`cache-simulator.ts`'s `missReason` does not yet distinguish "lost the
  race" from "no-matching-prefix."** Both currently report
  `no-matching-prefix` when an entry exists but is not yet `availableAt`.
  Correct cost-wise (confirmed by the dedicated tests), just coarser
  diagnostics than ideal; a cheap follow-up, not required for tonight's
  measurement.
