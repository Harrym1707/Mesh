## New-lever research: multi-agent fan-out (lever backlog P5)

### Why this lever, and why tonight

`docs/rnd/lever-backlog.md`'s P5 ("shared-prefix fan-out serialization") was
the most-fleshed-out, fully-specified, genuinely lossless candidate still
sitting at zero implementation: a provider's prompt-cache entry exists only
once the WRITING request's first response bytes arrive, not at send time,
so an orchestrator that fans several sub-agents out at once — all carrying
the same system+tools prefix — has every one of them racing to write that
prefix, none of them reading. P5's own measurement plan named the first
concrete step: "add entry-available-at-first-response-START concurrency
semantics to `cache-simulator.ts` IN THE SAME CHANGE and restate the
multi-agent band under them first (it will come down) — the lever's credit
is the delta against the corrected baseline, never the current optimistic
one." That was still undone; it is the literal next action P5 specifies, so
it is what got built.

This also matches the founder mandate's "multi-agent teams (sub-agent
fan-out re-sending shared context)" shape explicitly.

### What real frameworks actually do (so the fixture isn't invented)

Checked via WebSearch rather than assumed:
- **LangGraph**: a fan-out edge to several destination nodes runs all of
  them in the same "superstep" — concurrently, with the graph waiting for
  all before continuing (docs.langchain.com/oss/python/langgraph/
  graph-api-control-flow; langchain-ai.github.io/langgraph/how-tos/
  branching). This is genuinely simultaneous dispatch, not staggered.
- **CrewAI**: `akickoff()` / `kickoff_async()` plus `asyncio.gather`-style
  dispatch for tasks and crews run in parallel is the documented pattern
  for concurrent sub-agent work (docs.crewai.com/en/learn/kickoff-async).
- The existing `multiAgentTeam()` fixture in `evals/run-workload-matrix.ts`
  staggers its 5 sub-agents 4 seconds apart per round (`atSeconds: round *
  40 + slot * 4`) — which, now that the simulator can model TTFB at all,
  does NOT exercise a real collision (4s comfortably clears any realistic
  time-to-first-byte). It was not touched tonight; it is simply not the
  right fixture for this lever, and nothing about it needed to change for
  this work.

### The substrate fix: `cache-simulator.ts`

Added an opt-in `cacheAvailabilityDelaySeconds` option to `simulateCache`
(`packages/core/src/cache-simulator.ts`): when supplied, a written cache
entry only becomes matchable by a LATER request once
`writingRequest.atSeconds + delay(writtenTokens)` has passed; a request
arriving before that sees the entry as not-yet-available and reports a new,
distinct `missReason: "racing-write"` (not lumped in with ordinary misses).
Omitted (the default, used by every existing eval and test), the option is
a no-op — `availableAt = atSeconds + 0`, byte-for-byte the simulator's
long-standing instant-availability behaviour. Re-confirmed zero effect on
every existing fixture via the full test suite (523 → 541 passing tests)
and by re-running `run-agent-ab.ts` / `run-cache-decomposition.ts` and
diffing against README/evidence.md (see above — no drift). Four new tests
in `cache-simulator.test.ts` cover: default behaviour unaffected by an
explicit zero-delay; simultaneous same-prefix requests all collide under a
realistic delay; a request arriving after the delay elapses reads normally;
an explicit zero is indistinguishable from omitting the option entirely.

### The production lever: `FanOutLatch`

New module `packages/sdk-js/src/fan-out-latch.ts`. Pure send-timing fix, no
content mutation: `acquire(key)` lets the first request for a shared-prefix
key proceed immediately and returns a `release()` the caller must call once
the response's headers are in hand (success OR failure — release-on-error
is structural, not a special case, since the caller's own `catch` branch
calls the same function). A second request for the SAME key arriving while
the first is still in flight is held until release, bounded by a mandatory
`holdCapMs`: if the holder never releases (hung, slow, or simply over
budget), the hold expires and the waiter proceeds UNLATCHED rather than
stall — forfeiting that round's saving, never breaking the request. Keyed
on `{model, tools, system}` only (`fanOutLatchKey`), never on the per-agent
task content, so agents with genuinely different prefixes never contend.

Caught a real bug while writing the tests (not hypothetical): the first
implementation re-entered `acquire()` recursively after every wake,
including a HOLD-CAP TIMEOUT wake — so if the holder never released, each
waiter would re-queue and re-time-out every `holdCapMs`, forever, rather
than actually proceeding. Fixed by only recursing on an actual release;
a timeout returns a no-op release immediately. The "never stalls past the
hold cap" test (packages/sdk-js/src/fan-out-latch.test.ts) failed against
the first version and passes against the fix — exactly the kind of thing a
quality gate exists to catch before it reaches the proxy. 11 tests cover:
solo pass-through, holding a racer, release-on-failure, the hold-cap
timeout fix itself, three-way serialization, cross-key independence,
idempotent double-release, and constructor validation.

### Proxy integration (opt-in, conservative)

Wired into `packages/sdk-js/src/proxy.ts` behind a new, default-OFF
`MeshProxyOptions.fanOutLatch?: { holdCapMs }`. When configured, the proxy
only engages the latch for a request whose REDUCED body carries a non-empty
`system` or `tools` — a request with neither has nothing in common with any
sibling beyond the model and must never be serialized against one. Released
the instant the upstream `fetch()` promise resolves (success or error),
which is exactly the moment a provider's own response headers are in hand —
holding any longer (through body streaming) would add latency for zero
benefit. Three new integration tests in `proxy.test.ts`, against a REAL HTTP
stub upstream that measures actual wall-clock arrival gaps: two concurrent
same-prefix sub-agent requests are measurably held apart by the first's
simulated response delay; two concurrent requests with DIFFERENT shared
prefixes are not held back at all; and with `fanOutLatch` unconfigured,
behaviour is unchanged from today (sub-50ms arrival gap either way). All
three pass.

**What this does NOT yet do**, honestly: it does not check the per-model
cache minimum before engaging (condition 4 in P5 — the `system`/`tools`
non-empty gate is a cheap conservative proxy, not the real `countTokens`
check, which proxy.ts doesn't currently thread through to this call site);
it logs no real arrival timestamps for a live collision-rate measurement
(P5's own "top missing input"); and it has not been validated against live
provider traffic. It is also NOT enabled by default — a deployment opts in
by passing `fanOutLatch`.

### Measured result — honest, bracketed, not blended

New eval `evals/run-fanout-collision.ts` (`pnpm fanout:collision`), fixture:
8 rounds × 5 concurrent sub-agents sharing a 2,234-token system+tools block
(clears the 1,024-token minimum), each round's 5 dispatches at the identical
`atSeconds` (true simultaneity, per the LangGraph/CrewAI evidence above).
Three arms per scenario — NAIVE (today's pre-existing, now-corrected-away
optimistic simulator default), REAL (the actual uncorrected cost: every
round's collision modelled with a 1.5s TTFB estimate, cited from Artificial
Analysis's third-party Claude Sonnet provider benchmarks at a 10,000-token
input, ~1.16–1.96s across snapshots — if anything conservative for this
fixture's smaller 2,234-token prefix), and LATCHED (the same stream with
each round's non-first racer's dispatch moved forward by that same TTFB
estimate, which is exactly what `FanOutLatch` achieves on the wire, per the
`proxy.test.ts` integration tests proving the timing shift end-to-end).

The honest lever credit is always LATCHED vs REAL, never vs NAIVE — NAIVE
was never a real cost, so "beating" it is not a saving.

Two regimes, bracketing the one thing that is genuinely unmeasured (how
often a real deployment's idle gap between fan-outs exceeds the 5-minute
TTL), rather than asserting one blended number:

| scenario | spacing | real cost | latched cost | lever credit | collided calls |
|---|---|---|---|---|---|
| busy team (cache stays warm) | 90s | $0.1256 | $0.1040 | **17.2%** of real cost | 4/40 (round 0 only) |
| bursty ticket queue (TTL expires between tickets) | 600s | $0.3132 | $0.1415 | **54.8%** of real cost | 32/40 (every round) |

The more important finding than either percentage: in the busy regime, the
collision this lever fixes is a **cold-start cost, not a per-round tax** —
once any round's fan-out has written the shared prefix and a later round's
fan-out reads it inside the TTL, there is nothing left to collide on, so the
lever's value over a long busy session is small. In the bursty regime,
`real` costs MORE than not caching at all ($0.3132 vs $0.2682 uncached) —
stamping `cache_control` on a bursty multi-agent fan-out WITHOUT this lever
is a **net loss**, not merely a smaller win, because every collision pays a
1.25x write premium and reads nothing back, every single time. This is the
most actionable honest result of the night: the lever matters most
precisely on the deployment shape (ticket-queue-driven support/ops bots,
scheduled review agents) where blind cache-stamping would otherwise be
actively harmful.

Quality gate / replay-gate status: **none needed.** This is purely a timing
change — the bytes every sub-agent sends are byte-identical whether latched
or not; only WHEN the request is dispatched changes. No replay gate applies
(same class as the pre-existing volatility-guard suppression and last
night's below-minimum guard).
