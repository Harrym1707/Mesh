## Tonight's hardening: per-model cache minimum in the simulator

This closes the item `2026-10-25-NOTES.md` flagged and nobody had picked up
since: `cache-simulator.ts`'s `ANTHROPIC_CACHE_5M` / `ANTHROPIC_CACHE_1H`
policy constants hardcode `minimumCacheableTokens: 1_024`, regardless of
model. Real Anthropic traffic needs 2,048 tokens before a Haiku-class model's
prefix caches at all — and the *production* stamping code already knows this
(`anthropicCacheableMinimumTokens` in `packages/core/src/model-prices.ts`,
used by `packages/sdk-js/src/reduce-request.ts`). The simulator just never
called it. Harmless today because every published fixture is Sonnet-class,
but silently wrong the day any eval or customer-run simulation prices a
Haiku-class workload: it would claim a cache hit below 2,048 tokens that the
real API would never grant.

**Fix** (`packages/core/src/cache-simulator.ts`):
- Added `anthropicCachePolicy(base, modelId)`, which takes `ANTHROPIC_CACHE_5M`
  or `ANTHROPIC_CACHE_1H` and returns a copy with `minimumCacheableTokens` set
  from `anthropicCacheableMinimumTokens(modelId)` — 2,048 for Haiku-class,
  1,024 otherwise. Everything else on the policy (TTL, write/read
  multipliers) passes through untouched.
- `packages/core/src/savings-model.ts`'s `projectSavings` gained an optional
  `options.modelId`, resolved the same way when `minimumCacheableTokens` isn't
  given explicitly, falling back to the existing 1,024 default when neither is
  supplied — fully backward compatible.

**Tests added** (both files' `.test.ts`, 7 new, all passing):
- `anthropicCachePolicy` keeps 1,024 for a Sonnet id, raises to 2,048 for a
  Haiku id, and (the one that actually proves the bug): a prefix sized between
  1,024 and 2,048 tokens hits under the bare `ANTHROPIC_CACHE_5M` constant but
  correctly misses (`missReason: "below-minimum"`) once wrapped for a
  Haiku-class model id.
- `projectSavings` gets the matching three: Haiku id suppresses caching on a
  1,500-token stable segment where the default doesn't, a Sonnet id changes
  nothing, and an explicit `minimumCacheableTokens` still wins over a supplied
  `modelId`.

**Re-verified nothing published moved**: `run-cache-decomposition.ts`'s three
numbers (37.9% / 57.3% / 31.3%) and `run-agent-ab.ts`'s entire output are
byte-identical before and after (diffed the full stdout) — expected, since no
call site was switched to the new model-aware constructor; this is a
correctness fix for a currently-dormant gap, not a rewire of existing
measurements.

**Scope I deliberately did NOT do tonight**: wire `anthropicCachePolicy` into
the ~15 call sites across `evals/run-agent-ab.ts`,
`run-cache-decomposition.ts`, `run-workload-matrix.ts`,
`run-memory-agent-dedup.ts`, `run-replay-gate-freshcap.ts`. None of those
fixtures track a model id today (they're generically "Anthropic-shaped"), so
plumbing one through would be pure mechanical churn across the files that
produce every published headline, for zero behavioral change (every fixture
is Sonnet-class, so the minimum stays 1,024 either way). That's a bad
risk/reward trade for a dormant bug. The new function and tests make the fix
free to apply the moment any eval actually needs a Haiku-class simulation —
pass `anthropicCachePolicy(ANTHROPIC_CACHE_5M, modelId)` instead of the bare
constant at that call site.
