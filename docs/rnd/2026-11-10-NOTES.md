## New-lever research (step 3): RAG pipelines, cross-turn duplicate chunks

**Why this shape, why tonight:** the founder mandate's workload list
includes RAG pipelines explicitly. `docs/rnd/lever-backlog.md`'s run-2
section ("2026-10-27") already flags that nobody has done for RAG what
`2026-10-23` did for memory agents (`crossTurnMemoryDedup`) or what
`2026-10-24` did for RAG's *single-newline* case — that gap was still open
as of the last lever-backlog update and nothing since closed it.

**What already exists, checked first (lossless-first, per the method):**
`evals/run-workload-matrix.ts`'s "rag pipeline" shape is **stateless**
one-shots — no conversation history, one request per question. Its only
duplicate excerpts are WITHIN a single request (the same passage retrieved
twice for one query), and `dedupeRepeatedBlocks`'s own doc comment already
says this case is closed losslessly: "A RAG prompt that joins several
retrieved excerpts with `picks.join('\n')` ... an excerpt pulled twice is
still an exact duplicate line." Confirmed by reading the function — this is
real, shipped, lossless, and not re-litigated tonight.

**The gap:** real RAG deployments are frequently NOT stateless. Checked
against real framework behaviour (WebSearch, since no RAG framework is
vendored here to read directly): LangChain's `ConversationalRetrievalChain`
is deprecated in favour of `create_history_aware_retriever`, which
re-retrieves against a history-rewritten standalone question EVERY turn
rather than reusing a stored result. A LangChain forum thread on this exact
failure mode confirms retrieved content "piles up across turns" whenever an
app's state schema writes retrieval results into a message list with append
semantics (rather than keeping them as local, ephemeral variables) — which
is a common, unremarkable way to wire a chat loop, not a bug. A
practitioner Stack Overflow question independently reports the same
retriever returning the same content turn after turn while memory stores it
verbatim, bloating the prompt, and asks how to dedupe it. So: a
conversational RAG app that keeps history and appends each turn's
"Context:\n<chunks>\n\nQuestion: ..." block onto it will, on any topically
clustered follow-up sequence, resend a chunk already sent several turns
back — non-adjacent, usually not in leading position (a RAG turn's own
new content is `Context: ...\n\nQuestion: ...`, so the repeated chunk sits
after the "Context:" line, never truly leading). Checked both existing
levers against this shape:
- `duplicateContext` only ever sees one message's text at a time — it
  cannot know an EARLIER message already carried the same chunk.
- `crossTurnMemoryDedup` only matches a repeated LEADING block — a RAG
  chunk buried after "Context:\n" in a non-first position never matches,
  and even if it were leading, it does not repeat on literally every turn
  (only when retrieval happens to overlap), which the leading-block matcher
  does not require but a position-sensitive "restated vs not" design would
  need to handle differently anyway.

Neither lever reaches it. No genuinely lossless angle exists for this
specific case beyond what is already shipped (the within-request case):
removing a chunk from a LATER position changes where in the context window
the model sees it relative to the current question, which is exactly the
attention/recency risk `crossTurnMemoryDedup`'s own doc comment already
accepts as the reason it is LOSSY rather than lossless. Tried lossless
first, concluded (not assumed) that this is the same risk category, and
built it as such — honestly, not inflated.

### Built

- `packages/core/src/token-reduction.ts`: `dedupeRepeatedBlocksAcrossTexts`
  — generalizes `dedupeRepeatedLeadingBlock`'s cross-text matching to ANY
  block position (not just leading), at blank-line block granularity (never
  line-level, to keep the false-positive bar high across genuinely separate
  turns rather than one assembled prompt), skipping fenced code and blocks
  under a token minimum. A within-text duplicate is deliberately NOT caught
  here (left for `dedupeRepeatedBlocks`) — `seen` is only updated with a
  text's surviving blocks after that whole text is scanned, so the two
  levers' scope never overlaps. 8 new unit tests
  (`token-reduction.test.ts`), including non-adjacent/non-leading matching,
  code-fence exclusion, idempotence, and the within-text non-overlap
  guarantee.
- `packages/sdk-js/src/reduce-request.ts`: new opt-in, default-`false`
  config `ragCrossTurnDedup` (boolean or `{minimumBlockTokens}`), restricted
  to `user`-role turns for the same reason `crossTurnMemoryDedup` is (that's
  where an app glues retrieved context onto the call). Reports lever id
  `rag-cross-turn-dedup`, `lossless: false`, with the same replay-gate
  caveat text as `crossTurnMemoryDedup`. 10 new tests in
  `reduce-request.test.ts` mirroring that lever's test shape, including the
  case that matters most for this shape specifically: a turn that retrieves
  something NEW is left untouched, only a turn whose chunk has actually
  repeated gets rewritten.
- `evals/run-rag-conversational-dedup.ts`: new fixture — a 36-turn
  conversational RAG chatbot over a 10-passage corpus, topic drifting every
  3 turns so retrieval returns 2 overlapping passages for a run of turns
  before moving on (the exact "topically clustered follow-up" shape the
  research above describes), history kept and resent every turn. Three arms
  (raw / lossless stack / lossless + `ragCrossTurnDedup`), same honesty
  structure as `run-memory-agent-dedup.ts`.

### Measured

```
node --import tsx evals/run-rag-conversational-dedup.ts
```

| arm | tokens before→after | cost | levers |
|---|---|---|---|
| A. raw | 165,096 → 165,096 | $0.3950 | none |
| B. lossless stack | 163,836 → 164,797 | $0.3950 | cache-ttl-suppressed×5, cache-ttl-5m×31 |
| C. B + ragCrossTurnDedup | 163,836 → 87,820 | $0.2412 | rag-cross-turn-dedup×35, cache-ttl-suppressed×8, cache-ttl-5m×28 |

- **B vs A (lossless, qualified): 0.0%.** As designed: this fixture's system
  prompt sits below the 1,024-token cacheable minimum (same reasoning as
  `run-memory-agent-dedup.ts`), so the cache stamp earns nothing, and the
  fixture deliberately contains no WITHIN-message duplicate chunks (that
  case is already closed elsewhere, see above) — nothing for the lossless
  stack to do here is itself the honest confirmation that this shape's gap
  is real, not already covered.
- **C vs B (ragCrossTurnDedup's own effect, LOSSY, candidate only): 38.9%.**
  Same order of magnitude as `crossTurnMemoryDedup`'s measured 58.0% on the
  memory-agent shape (lower here because this fixture's cross-turn overlap
  is partial — only 2 of each turn's 2 chunks repeat for 2 of every 3 turns,
  not every chunk on every turn).
- **C vs A: 38.9%** (same as C vs B since B vs A is 0.0% on this fixture).

**Quality gate / replay-gate status:** none run. This is a candidate, not a
qualified win — per the method, "a lever worth 2% is reportable, a lever
that loses is a finding, never inflate," and a lossy lever's percentage is
never billed before its own replay-gate pass. Correctly labelled lossy in
the code (`lossless: false`) and in every report line above.
