## Hardening: bound `CachePrefixVolatilityGuard`'s memory on long-horizon histories

**The gap.** `packages/sdk-js/src/cache-volatility-guard.ts` tracks, per conversation,
whether its message history has only ever EXTENDED turn over turn (a client that
rewrites history breaks the provider's cache, so the guard withholds the newest-message
breakpoint when it detects that). Before tonight, it proved this by storing the full
array of one hash per message (`messageHashes: string[]`) in the conversation entry,
forever, for as long as that conversation stays in the guard's LRU (`maxConversations`,
default 1000). An autonomous agent — the exact workload shape the mandate calls out
("autonomous long-horizon agents... history growth") — can run for hundreds of turns
with history resent every turn; this guard's own per-conversation memory grew with it,
unbounded, for the entire lifetime of a tracked conversation. Nothing downstream ever
read anything from that array except the equality check at the shared prefix length —
the guard never needed to know WHICH message changed, only WHETHER one did.

**The fix (lossless, behavior-preserving).** Replaced the stored array with a hash
chain: `chain_i = H(chain_{i-1} || digest(message_i))`, seeded from a fixed constant so
an empty-vs-populated history can never collide with real content. Two conversations'
chains agree at position `n` iff their first `n` messages agree, by the same digest
collision-resistance the old per-index array comparison already relied on — so
`historyExtends` is decided identically, just from two fixed-size scalars
(`historyChain: string`, `historyLength: number`) instead of an array sized to the
conversation. Computing the chain is one pass over the incoming messages, the same
O(length) cost `messages.map(digest)` already paid every turn — this changes what is
STORED between turns, not the per-turn work. `prefixHash` (the `{tools, system}` or
`stampedPrefix` comparison) was already O(1) and is untouched.
