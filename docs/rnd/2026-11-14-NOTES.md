## New-lever research: tool-schema minification on Pydantic-shaped catalogues

### Why this workload / shape

Picked the shared-tool-catalogue shape (multi-agent teams and autonomous
long-horizon agents both resend the same tool catalogue every turn — the
doctrine's two highest-priority verticals). `docs/rnd/lever-backlog.md`'s tail
already named this: **T1, tool-schema canonical ordering + pydantic-aware
minifier extension** — "safest lever on the list," unreviewed, queued for
adversarial review. Tool-schema compaction itself already shipped
(`packages/core/src/tool-schema.ts`, on by default via `toolSchemas: true`),
so tonight's job was specifically the Pydantic-aware extension T1 calls for.

### Research (real framework behaviour, not assumption)

WebSearched Anthropic's and OpenAI's own documented `$ref`/`$defs` support in
tool schemas, and LangChain's actual `convert_to_openai_tool` source:

- Both providers document support for `$ref` into `$defs` in tool/function
  schemas. The Anthropic Python SDK's `transform_schema` helper recurses into
  `$defs` rather than stripping it; a `pydantic-ai` test shows a nested
  `Address` model sent to Claude as `$ref: "#/$defs/Address"` directly, no
  client-side resolution. A live GitHub issue reports Claude mishandling a
  `$ref` to an enum inside `$defs` (returns `null`) — independent evidence
  that `$ref`/`$defs` reaches the model's own schema-reading path for real,
  on real traffic, today.
- LangChain's `convert_to_openai_tool` (OpenAI-bound path only) actually
  *dereferences* `$ref` and deletes `$defs`/`definitions` client-side before
  the request ever reaches MESH. So the exposure is specifically: direct
  Anthropic `tool_use`, MCP tool registration, and any non-OpenAI-bound
  LangChain/CrewAI/AutoGen integration that passes a raw Pydantic
  `model_json_schema()` output through — all of which keep `$ref`/`$defs`
  intact on the wire.

### The finding: a live correctness bug in the shipped minifier

`packages/core/src/tool-schema.ts`'s `PLUMBING_KEYS` included `$defs` and
removed it **unconditionally**, on every tool, with no check for whether
anything referenced it. `toolSchemas !== false` is the production default
(`packages/sdk-js/src/reduce-request.ts`), so this ran on every tool
catalogue containing `$defs` that passed through MESH with default config —
which, per the research above, is most non-OpenAI-bound Pydantic-generated
tool traffic. The result: every `$ref: "#/$defs/Name"` pointer in that
catalogue was left dangling, because the thing it pointed to was deleted. That
is schema corruption shipped as a "lossless" compaction, not a token saving
with a quality cost — it is a correctness defect, full stop, and it has been
live since this lever shipped (no fixture in the existing test suite or
`evals/run-workload-matrix.ts`'s `TOOLS` fixture used `$defs`/`$ref` at all,
which is exactly why nothing caught it).

Fixed tonight, not filed for later: this is a bug in an already-shipped,
on-by-default lever, and "quality gates only get stricter" does not wait for
a hardening night when the gate is already broken in production.

### The fix (packages/core/src/tool-schema.ts)

1. Removed `$defs` from `PLUMBING_KEYS`. Added reference-closure tracking:
   `collectSeedRefs` finds every `$ref` the *usable* schema actually makes
   (skipping definitions containers themselves); `liveDefinitionNames` walks
   that seed set transitively through each referenced definition's own body
   (so `A` referencing only `B`, which references `C`, keeps `C` too).
   Handles both `$defs` (2020-12, Pydantic v2) and legacy `definitions`
   (draft-07, Pydantic v1 and older generators) identically.
2. In `prune`, a `$defs`/`definitions` container now keeps every entry a live
   `$ref` reaches (still recursively pruned for genuine plumbing and
   redundant titles *inside* each kept entry) and drops only entries nothing
   reaches — recorded as a new lossless change kind, `unused-definition`.
   An empty resulting container is dropped entirely (nothing points at it,
   so removing it changes zero reachable bytes).
3. Scoped per-tool (`currentLiveDefinitionNames` recomputed before each
   tool's `prune` call): `$defs` in Pydantic output is local to each tool's
   own parameter schema, not catalogue-wide, and tool names are not
   guaranteed unique enough to share one global reference count safely.
4. Added `canonicalOrder` (opt-in, default `false`): sorts the retained tool
   array into a stable name order. Lossless — the set and schema of every
   tool is unchanged, only array position — but real multi-agent/autonomous
   frameworks rebuild their visible tool list from a mutable registry each
   turn (which sub-agents are active, which tools are currently permitted),
   so the array order is not always byte-stable turn to turn even when the
   tool SET is. An unstable order breaks the cached system+tools prefix on
   every such turn for no reason; canonicalizing it protects the prefix. This
   is T1's other half. Wired through `reduce-request.ts`'s
   `toolSchemas: { canonicalOrder: true }` config flag — had to special-case
   the call site, because a pure reorder saves 0 tokens and the existing
   `if (saved > 0)` guard would have silently discarded it.
5. Tests: `packages/core/src/tool-schema.test.ts` gained 10 cases (the
   regression itself, transitive-chain survival, legacy `definitions`,
   plumbing/title cleanup still applying inside a kept definition, and
   `canonicalOrder`'s ordering + idempotence + cross-turn identical-serialization
   behaviour). `packages/sdk-js/src/reduce-request.test.ts` gained 5
   integration cases at the `reduceRequest()` level. 523 → 537 tests, all
   green; the pre-existing 18 `tool-schema.test.ts` cases needed no changes.

### Measured (evals/run-tool-schema-pydantic.ts, new fixture)

Built a Pydantic-v2-shaped fixture matching the research above: 10 tools (the
same catalogue size as `run-workload-matrix.ts`'s `TOOLS`), each with a nested
`ContactInfo → Address` model via `$ref`/`$defs` (every tool actually uses
both), and half additionally carrying an `ErrorEnvelope` definition from a
shared models module that those tools' own parameters never reference — the
realistic case of one Pydantic schema module exported once and reused across
many tool definitions.

- **Part A — regression reproduction.** Confirmed 10/10 tools would ship with
  a dangling `$ref` under the pre-fix code (reproduced the exact old
  `PLUMBING_KEYS`-based stripping inline, since that code no longer exists to
  call directly); 0/10 broken after tonight's fix.
- **Part B — unused-definition pruning (new lossless lever).** 4,136 → 2,921
  tokens on the fixture catalogue (29.4% smaller; includes the pre-existing
  plumbing/redundant-title tier too). Of that, the new unused-definition
  pruning alone accounts for 320 tokens across 5 dead `ErrorEnvelope`
  entries — real, honest, lossless, and specifically the savings the pre-fix
  code could never isolate correctly because it deleted `$defs` wholesale
  instead of checking what's referenced.
- **Part C — canonical order vs cache stability.** Built a 30-request
  multi-agent-team stream (5 agents × 6 rounds, matching
  `run-workload-matrix.ts`'s shape) where the tool array is reordered between
  rounds by a deterministic shuffle (a stand-in for a framework that rebuilds
  its visible tool list from a mutable registry). Ran both arms through
  `reduceRequest` then `simulateCache` (`ANTHROPIC_CACHE_5M`, catalogued
  Sonnet 5.5 prices): without `canonicalOrder`, hit rate 76.7%, cost $0.131,
  misses are `below-minimum` (the shared prefix across differently-ordered
  JSON collapses to almost nothing) not `no-matching-prefix`; with
  `canonicalOrder`, hit rate 95.5%, cost $0.086 — **34.1% lower cost**, same
  tools, same schemas, same messages, only array order surviving the resend.

Honesty labels, stated in the eval's own output: Part A/B are measured
directly from the code. Part C is **measured on this harness's own fixture,
mechanism-and-upper-bound only** — there is still no timestamped capture
(open item #3 in `lever-backlog.md`, flagged every night it's come up) showing
how often production tool arrays actually reorder turn-to-turn, so the
34.1% is not a population-wide claim, exactly the same caveat P5's
fan-out-latch lever already carries for the identical reason.

### Quality gate / replay-gate status

None needed for any of tonight's three pieces — the `$defs`/`$ref` fix is a
strict correctness restoration (nothing the model can reach changes; it can
only become reachable again where it had been wrongly removed), unused-
definition pruning only removes schema nothing can ever reach via `$ref`, and
`canonicalOrder` changes array position, not tool identity, name, or schema
content. All three are lossless by construction, matching the class every
other shipped tier of `tool-schema.ts` already carries.

### What shipped vs what's still opt-in

- `$defs`/`$ref` fix and unused-definition pruning: **on by default**,
  exactly like the pre-existing plumbing/redundant-title tier they extend —
  `toolSchemas !== false` is already the production default, no new flag.
- `canonicalOrder`: **opt-in**, `toolSchemas: { canonicalOrder: true }`. Not
  wired into Theo's policy system (`knownLeverIds()` /
  `ENFORCEABLE_LEVERS` in `packages/sdk-js/src/theo-policy.ts`) — it is
  reachable today only via direct `reduceRequest()` config, not via a
  published Theo policy. Deliberately left that way: tonight's own
  adversarial pass is the backlog's T1 review, not a full product-surface
  wiring, and claiming Theo-governability without having built it would be
