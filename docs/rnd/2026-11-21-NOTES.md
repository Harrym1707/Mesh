## New-lever research: multi-agent fan-out, the shared-prefix cache race (lever P5)

### Workload shape studied

Multi-agent teams: an orchestrator starts several sub-agents sharing one
system+tools prefix. `docs/rnd/lever-backlog.md`'s P5 (shared-prefix fan-out
serialization) was the top unshipped lossless candidate — "the most
genuinely lossless lever in the portfolio" — blocked only on "no capture in
the repo carries timestamps" and on the cache simulator having no
concurrency semantics at all.

Checked how real frameworks actually dispatch sub-agents, since the
existing `evals/run-workload-matrix.ts` multi-agent fixture staggers its
five agents by 4 seconds within each round — which, it turns out, was never
exercising a race, because 4 seconds is already enough for a real write to
land. Via WebSearch: LangGraph's `Send` API runs every dispatched node
within one **superstep** — genuinely concurrent, not staggered; CrewAI's
`akickoff_for_each` / `asyncio.gather(*[crew.akickoff(...) for ...])`
pattern starts every kickoff together for the same reason (its docs
recommend `akickoff()` specifically for high-concurrency fan-out). Neither
framework serializes sub-agent starts — concurrency is the point of fanning
out. So the realistic shape is N requests sharing a prefix arriving at
*the same instant*, not spaced apart.

### What was actually broken, found by trying to measure it

`packages/core/src/cache-simulator.ts` had no concept of a cache write
taking any time to become visible. It processes a request stream in
timestamp order and pushes each entry into the live set the instant that
request is "sent" — so two requests at the identical timestamp already
looked like one write followed by one 0.1x read, with **no latch, and no
latency cost**, because nothing modeled the alternative. Every number this
repo has ever published for the multi-agent shape was earned by a 4-second
stagger that avoids the race entirely; nothing in the repo had ever measured
the race itself, and the simulator could not have gotten it right if asked,
because the field to describe "how long after a write starts does it become
readable" did not exist. This is exactly backlog P5's own warning: "retire
the ~92% headline until collision frequency is measured... the lever's
credit is the delta against the corrected baseline, never the current
optimistic one."

### The fix: `writeAvailabilityDelaySeconds`

`packages/core/src/cache-simulator.ts`: added an optional
`writeAvailabilityDelaySeconds` field to `CachePolicy`. An entry is now
tracked with an `availableAt` timestamp (write time + the delay) and is only
eligible to match a later request once `request.atSeconds >= entry.availableAt`.
**Every exported policy (`OPENAI_CACHE`, `ANTHROPIC_CACHE_5M`,
`ANTHROPIC_CACHE_1H`, `ANTHROPIC_NO_CACHE`) leaves the field unset**, so it
defaults to 0 and every existing simulation — every published number —
reproduces bit-for-bit (confirmed above). A new `missReason` value,
`"not-yet-available"`, distinguishes "the entry exists but isn't visible
yet" from `"expired"` (TTL lapsed) so a simulation's miss breakdown stays
honest about which failure mode actually happened. 4 new tests in
`cache-simulator.test.ts`: the default (unset delay) reproduces today's
optimistic same-instant behavior unchanged; with a delay set, two
simultaneous requests both miss and both write; a request arriving exactly
at the delay boundary reads the now-available entry; the delay never
changes a below-minimum verdict.

### The lever: `FanOutLatch`

New `packages/sdk-js/src/fanout-latch.ts`: a small, framework-agnostic
`FanOutLatch` class plus `fanOutPrefixHash({model, tools, system})` (the
same {model, tools, system} span the cache stamp and the volatility guard
already key on). The first request for a prefix is the leader and proceeds
immediately; `acquire()` holds every later request for the same prefix
until the leader calls `release()` or `maxHoldMs` elapses (default 5000ms)
— whichever comes first, so a stalled or errored leader can never hang a
follower; the follower just proceeds exactly as it would without the latch.
12 unit tests cover leader/follower assignment, multi-follower release,
the fail-open timeout, re-leadership after release, cross-prefix
independence, and the constructor's input validation.

Wired into `packages/sdk-js/src/proxy.ts` behind a new, **opt-in, default-off**
`fanOutLatch` option on `MeshProxyOptions` (`boolean | FanOutLatchOptions`).
The hash is computed from the *reduced* request's `{tools, system}` (post
MESH's own levers, same convention as the volatility guard, so MESH's own
transforms are never mistaken for two different prefixes) plus the model
id. `fetch()`'s promise resolves exactly when response headers arrive —
precisely the "first byte" moment a provider's cache write commits — so the
leader calls `release()` right there, in both the success and the
upstream-error path (the latter via the existing `catch`), so a follower is
never held past a leader's own failure. 4 new proxy-level integration
tests: a follower sharing the leader's prefix is held until the leader's
(artificially delayed) headers resolve; with `fanOutLatch` unset, nothing
changes (confirms zero default-behavior drift); two concurrent requests
with *different* prefixes never hold each other up; a follower is released
immediately, not after the full timeout, when the leader's upstream call
errors outright.

Test count: 1205 → 1225 (12 + 4 + 4 new, 1 pre-existing unaffected).
`pnpm build` clean throughout.

### Measurement: `evals/run-fanout-latch.ts`

Fixture: 5 sub-agents (the same preamble/tool-catalogue shape and size as
`run-workload-matrix.ts`'s multi-agent fixture, for comparability) × 6
rounds, **every round genuinely concurrent** (all 5 agents at the exact
same `atSeconds`), rounds spaced past the 5-minute TTL so each round is its
own fresh race rather than riding a still-warm cache from the previous
round.

| arm | cost | vs corrected baseline |
|---|---|---|
| naive concurrent, race modeled (corrected baseline) | $0.2389 | — |
| naive concurrent, OLD simulator (no delay concept) | $0.1068 | this is what every prior eval effectively assumed — already at the latch's answer, for free, with no latch and no latency cost |
| **with the fan-out latch** | **$0.1068** | **55.3% lower** |

Self-checked in the script itself (throws if violated, not just printed):
naive — every one of the 30 requests writes (30/30); latched — exactly one
write per round (6/30), the rest reads.

**Honest band: 55.3% token-cost reduction on this shape, entirely dependent
on an assumed 1.5s write-availability delay that is a placeholder, not a
measurement** (no capture in this repo carries timestamps, so neither the
delay nor real collision frequency can be derived from traffic yet — the
same open item P5's adversarial review already named). Because the same
assumption sizes both the baseline and the lever, the *qualitative* finding
(uncorrected simulations silently give fan-out traffic the latch's benefit
for free; the real race is a genuine loss the latch genuinely repairs) does
not depend on getting 1.5s exactly right, but the 55.3% headline does, and
must not be quoted outside this caveat. Latency is explicitly NOT priced
here — held followers pay real wall-clock cost, which is exactly why
`fanOutLatch` ships opt-in and bounded (`maxHoldMs`, fail-open) rather than
as a default, per the adversarial conditions already on file for P5.

### Quality / replay-gate status

None needed. This is the P5 class of lever: bytes untouched, only send

without the latch (never worse than today, never silently wrong). No
