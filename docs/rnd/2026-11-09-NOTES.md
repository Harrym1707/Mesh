## New-lever research: RAG pipelines

### Grounding (WebSearch, before designing anything)

Two real, sourced facts shaped the design, not assumptions:

1. **Anthropic's own prompt-caching guidance**: for a knowledge base under
   ~200K tokens, cache the WHOLE knowledge base rather than caching per-query
   retrieval results. Rationale given: the provider's cache matches an EXACT
   prefix, and two different questions almost never retrieve the identical
   chunk SET in the identical ORDER, so per-query inlined picks essentially
   never repeat byte-for-byte even when most of the underlying text does.
2. Third-party write-ups (unverified numbers, but a consistent qualitative
   pattern across several independent ones) describe retrieved-document
   duplication across RAG calls as a real, named cost driver ("context
   window bloat"), caused by conservative top-k and near-duplicate retrieval
   — i.e. the inefficiency this lever targets is a recognized failure mode,
   not a corner case invented for this fixture.

This also explains a fact already on record in this repo:
`evals/run-workload-matrix.ts`'s existing "rag pipeline" arm has its
cache-ttl-5m stamp SUPPRESSED (`2026-10-25-NOTES.md`) because the bare system
prompt never clears the 1,024-token cacheable minimum. The shape has nothing
stable and large enough to cache *until something hoists the repeating
retrieval content itself into the prefix* — which is exactly what Anthropic's
own guidance says to do, and exactly what was missing.

### The lever: `ragCorpusCache`

New files/changes:
- `packages/core/src/token-reduction.ts`: `growRagCorpus` (pure: grows an
  append-only, cache-stable corpus from known + this-call chunks, resolves
  this call's chunks to stable indices, all-or-nothing against a token
  budget) and `renderRagCorpusBlock` (renders the corpus as the stable
  system-prompt block). 9 new tests in `token-reduction.test.ts`.
- `packages/sdk-js/src/reduce-request.ts`: `ragCorpusCache` config option +
  `applyRagCorpusCache`. Given `{ knownCorpus, chunks }` (the caller's own
  bookkeeping — MESH holds no cross-request state of its own, matching this
  file's existing "nothing here may break a request" / "never guess" ethos),
  it hoists `chunks` into the corpus, placed in the STABLE region of
  `system` (before any `repairCachePrefix`-relocated volatile tail, so a
  cache breakpoint can cover it), and replaces each chunk's literal inline
  text in the last message with a short `[corpus#N]` reference. All-or-
  nothing per call: if the request's shape doesn't match exactly (no system
  prompt, last message not a plain string, or it doesn't literally contain
  every chunk) or growing the corpus would exceed `maximumCorpusTokens`
  (default 8,000), nothing is touched. `summary.nextKnownCorpus` carries the
  grown corpus back to the caller to resupply next call. 8 new tests in
  `reduce-request.test.ts`, including one proving the corpus block lands
  BEFORE a prefix-repaired volatile tail, not after it.

**Classified LOSSY, not lossless**, on purpose, despite deleting no chunk's
text: every chunk a question depends on is still sent, in full, inside the
corpus block — but it is no longer adjacent to the question, and the model
must resolve a `[corpus#N]` reference instead of reading the excerpt where it
used to sit. That is the same category of behaviour-risk `crossTurnMemoryDedup`
already carries (information present, not removed, but relocated away from
where the model expects it), so it gets the same treatment: `estimatedTokensSaved:
0` on the change record (the real effect is a cache-rate change across the
stream, not a per-call token count — per-call raw tokens typically RISE,
since the corpus block is now part of every request), and a `detail` string
naming the replay-gate requirement explicitly. **Not wired into
`theo-policy.ts`**: every other Theo-enforceable lever is a static per-user
toggle a policy document can carry, but this lever needs per-REQUEST data
(`chunks` — the actual retrieved excerpts) that only the caller's own
request has at call time, not something a policy document can supply ahead
of it. Forcing it into that model would be a worse fit than leaving it as an
explicit SDK-level config option a caller wires directly; flagging this
mismatch honestly rather than papering over it with a toggle Theo can't
actually drive.

### Fixture and measurement

`evals/run-rag-corpus-cache.ts`: a 16-clause knowledge base, 80 one-shot
queries, deterministic pseudo-retrieval (3 "always relevant" clauses present
in nearly every query, like a definitions/governing-law section a real
retriever keeps surfacing, plus 1-2 question-specific clauses round-robining
across the rest of the corpus — so the full corpus gets touched, and reused,
many times over the run). Three arms (A raw / B lossless+5m-stamp / C
B+ragCorpusCache), same honesty convention as `run-memory-agent-dedup.ts`.
Measured on catalogued `claude-sonnet-5-5` prices via the same provider-rule
cache simulator every other eval in this repo uses — no new pricing model.

| spacing | A raw | B (lossless+stamp) | C (+ragCorpusCache) | C vs B |
|---|---|---|---|---|
| 20s apart (busy RAG endpoint) | $0.1883 | $0.1883 (stamp suppressed 80/80, hit rate 0%) | $0.1549 (stamp fires 68/80 once the corpus clears 1,024 tok; hit rate 89%) | **+17.8%** |
| 400s apart (sparse, TTL-hostile control) | $0.1883 | $0.1883 (suppressed 80/80) | $0.3968 (stamp fires 68/80, hit rate 0%) | **−110.7%, a measured loss** |

Both rows are reported, neither is hidden. The busy-endpoint result is the
grounding hypothesis working exactly as designed: the corpus grows past the
1,024-token minimum around query ~12 (of 80), the cache-ttl-5m stamp starts
firing on its own (68/80 stamped, 12/80 still below minimum early on — no
manual gating needed; the existing production stamp logic and the simulator
apply the identical minimum-on-the-matched-prefix rule, so this validates the
integration end-to-end), and 17.8% of B's cost disappears purely from giving
the provider's cache something stable enough to actually hold onto. The
sparse row is the SAME known failure mode `cacheTtl` already carries on this
fixture family (write premium paid every call, TTL never survives to a read)
— reported as a finding per the founder mandate ("a lever that loses money
counts against FLUX"), not smoothed over. A real deployment only wants this
lever on a workload dense enough to keep the corpus's cache entry alive,
exactly the same caller-flagged-workload discipline `cacheTtl`/
`executionTier` already require.
